# Project Scope: Behavioral Insider Threat Detection Tool (UEBA)

## 1. Problem Statement
Insider threats come from people who already have legitimate access, so
signature-based tools often miss them. This project builds a UEBA
(User and Entity Behavior Analytics) pipeline in Python. It learns each
user's normal behavior from activity logs, flags unusual behavior, and
gives each user a daily risk score so a SOC analyst can triage the alerts.

## 2. Goals
- Build per-user, per-day behavioral features from log data using pandas.
- Detect anomalies with unsupervised models from scikit-learn.
- Produce a daily risk score per user and a ranked alert list.
- Evaluate the alerts honestly against the dataset's answer key.
- Document how an analyst would triage each type of alert.

## 3. Threat Scenarios in Scope
| # | Scenario | Suspicious behavior | MITRE ATT&CK |
|---|----------|--------------------|--------------|
| 1 | After-hours access | Login at 2 AM by a user who normally works 9 to 6 | T1078 Valid Accounts |
| 2 | Removable media use | Sudden USB activity by a user who rarely or never uses it | T1052.001 Exfiltration over USB |
| 3 | Large data copy to removable media | Far more files copied to a USB drive than the user's normal | T1052.001 Exfiltration over USB; T1074 Data Staged |

## 4. Data
- Source: CERT Insider Threat Test Dataset, release r4.2, published by
  Carnegie Mellon University (CERT Division, with ExactData). Licence: CC BY 4.0.
- The data is synthetic (generated by a program), not from a real company.
  This is stated in the README and on my resume.
- Files used in Phase 1:
  - logon.csv: logon and logoff events (user, PC, time)
  - device.csv: USB connect and disconnect events
  - file.csv: each file copied to a removable media device
  - answers file: used only to evaluate results, never for training
- Raw data is not uploaded to this repository. The README explains where to
  download it.

## 5. Approach
1. Load, clean and explore the logs.
2. Create features per user per day (for example login hour, number of USB
   events, number of files copied).
3. Build a baseline of normal behavior for each user.
4. Score deviations from the baseline with an anomaly detection model.
5. Convert scores into risk levels and a ranked alert list.
6. Check the alerts against the answer key and report what was measured.

## 6. Output
- A daily risk score per user.
- A ranked alert list showing why each user was flagged.
- Short triage notes: what an analyst should check next for each alert type.

## 7. Project Phases
**Phase 1: working core.** logon, device and file features, per-user
baseline, Isolation Forest, risk scores, ranked alerts, evaluation, README.

**Phase 2: depth (planned, started only after Phase 1 is finished).**
Richer features, peer-group comparison using LDAP role data, web browsing
logs (http.csv), and a second model for comparison.

**Phase 3: SOC layer (planned).** Plain-language alert explanations, a
triage guide, false-positive analysis and MITRE ATT&CK mapping per alert type.

A phase is marked complete only when it runs end to end and is documented.

## 8. Out of Scope
- Real-time or streaming detection
- Deep learning models
- Web dashboards or applications
- Cloud deployment
- Any claim about performance on real enterprise networks

## 9. Known Limitations
- An anomaly is not the same as a malicious act. False positives are
  expected, for example an employee working late before a deadline.
- Results come from one synthetic dataset and cannot be generalized to real
  environments.
- The dataset is "dense needles": it has an unrealistically high amount of
  malicious activity compared with a real organization, so results here will
  likely look better than real-world performance.
- The dataset deliberately contains missing logons and unmatched USB
  connect events (simulated dirty data), which affects feature quality.
- The MITRE ATT&CK mapping describes what each scenario resembles. It does
  not prove an attack happened.

## 10. Success Criteria
- The pipeline runs end to end, from raw logs to a ranked alert list.
- Every feature and model choice can be explained.
- The README reports only results that were actually measured, along with
  the limitations.
